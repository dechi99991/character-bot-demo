
- `✅ applied` — 承認 + TODO化 / フィロソフィー反映済み

### [2026-06-22] AI開発の要件復元フロー（Implementation → Requirements Recovery → Hearing Sheet）
- **内容**: チャット駆動でAIと開発を進めると、「PMの明示指示」と「AIが会話の余白で自律決定した実装判断」がコードに混在し、後から区別がつかなくなる。これを解く逆方向ワークフローとして「実装→要件復元→ヒヤリングシート化」の3ステップを確立した。
  - **Step1 実装読解**: 全主要ファイルを読み、何がどう実装されているかを事実として把握する（推測しない）。
  - **Step2 要件復元（requirements-recovery.md）**: 実装からMECEに要件を書き下し、各要件に「明示指示 / AI暗黙判断 / 要確認」の3タグを付ける。核心思想は「**実装が存在する≠要件として合意された**」。AIの先走りを `AI暗黙判断` として可視化し、合意未取得を `要確認` として隔離する。
  - **Step3 ヒヤリングシート化（requirements-hearing.md）**: `要確認` タグの項目を、選択肢付きQ&A合意書に変換。優先度（High/Medium/Low）と確認先（PM社内判断 vs クライアント決裁）を分離する。
- **今回のデモケースでわかったこと**:
  1. **暗黙判断は想像以上に多い**: 全40要件中、AI暗黙判断16件・要確認9件。明示指示は15件のみ。チャット駆動開発では実装の6割が「合意なしにAIが決めたこと」だった。
  2. **コードコメントと実装の乖離を炙り出せる**: `admin/page.tsx` のコメント「認証なし」と実装（middlewareでBasic認証後付け）の矛盾、`PROGRESS.md` のSVG表が背景を「CSSグリッド」と古いまま等、復元作業が副産物として陳腐化ドキュメントを検出した。
  3. **コンプラ矛盾を構造的に発見**: S2「他社ブランド名禁止」ルールと、知識ベースに他社実名（TEA BUCKS等）が記載されている矛盾を、要件を並べたことで発見できた。個別レビューでは見落としやすい。
  4. **「確定版」表記の罠**: コードコメントが「審査済み確定版・変更禁止」と主張しても、誰が確定したか（PM/クライアント/AI）が追跡できないものは `要確認` に落とすべき。AIの自己申告を合意と誤認しない。
- **汎用テンプレートとしての活用可能性**: このフローは tayumano 案件固有ではなく、**チャット駆動でAIに実装させた全プロジェクトに適用できる汎用パターン**。特に (a) プロトタイプを本番化する前 (b) 受託先へ引き継ぐ前 (c) クライアント承認を取る前 の3タイミングで、3タグ分類が「合意の棚卸し」として機能する。要件復元書のREQフォーマット（タグ/現状実装/根拠経緯/懸念）とヒヤリングシートのQフォーマット（現状/確認事項/選択肢A-C/優先度/確認先/回答欄）はそのまま流用可能。
- **原文脈**: 2026-06-22 セッション。チャット駆動で開発したキャラクターBotプロトタイプについて、実装から要件を逆算復元するタスクを実施。
- **関連**: `docs/requirements-recovery.md`（40要件）, `docs/requirements-hearing.md`（25問）

### [2026-06-15] In-Memory Singleton は Vercel サーバーレスでの CRUD プロトタイプに使える
- **内容**: Vercel サーバーレス環境でも module-level singleton は warm インスタンス内で生きる。Cloudflare D1 実装前のプロトタイプとして「データが消えることを明示した上での InMemory CRUD」は動作確認に十分機能する。追加パッケージゼロで即デプロイできる利点が大きい

- **関連**: `lib/db/index.ts`（InMemoryDataStore）, commit `1d38b5d`

### [2026-04-30] レビュー前マージ時の事後通知は3経路の冗長化が信頼性を上げる
- **内容**: コードオーナー不在で WRITE 権限保有者がレビュー前マージした際、事後通知は (a) 既存 PR へのコメント / (b) 後続 PR の作成 / (c) リポジトリ内の永続ドキュメント（progress-docs/PROGRESS.md 申し送りセクション）の3経路を併用すると、相手の作業タイミング・通知設定に依存せず確実に到達する。特に (c) は pull 時に自動で目に入るため「Slack 1回投稿で見落とし」を構造的に防ぐ
- **原文脈**: 2026-04-30 PR #1 マージ後セッション。WRITE 権限で先行マージしたあと dechi さんへの申し送り経路をどう設計するかを検討
- **関連**: PR #1 (#issuecomment-4349523026), PR #2

### [2026-04-30] GitHub の auto-delete-branch 設定後はローカル stale ref が残るので fetch --prune が必要
- **内容**: GitHub PR マージ時に branch auto-delete が動くと、ローカルの `git branch -a` には依然 `remotes/origin/feature/xxx` が表示される。`git push origin --delete` は「remote ref does not exist」エラーになる。`git fetch --prune` で stale ref を解消するのが正規ルート
- **原文脈**: 2026-04-30 PR #1 マージ後にリモートブランチ削除を試みた際に発生
- **関連**: なし
