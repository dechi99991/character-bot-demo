## 1. レビュー回答（§9の6問への回答）

### Q1. ハイブリッド制御の切り分けは実装上現実的か

現実的です。「ハードガードレール（機械的フィルタ）」と「ソフト推薦（LLM判断）」の分離は実装可能で、今回その思想をそのままシステムプロンプトの構造に落とし込みました。

ただし重要な補足が一点あります。現状の実装は **ハードガードレールも含めて「プロンプトベース（LLMに守らせる）」** です。具体的には、商品カタログにカフェイン量・味プロファイル等の全属性を露出させ、「①カフェイン除外 → ②苦手除外/明示指定 → ③好み必須 → ④初心者導線」の順で機械的にフィルタするようLLMに明示指示しています。

一方で、**カフェイン除外だけは安全に直結する**ため、本来はコード側で先にフィルタする方が確実です（LLMは確率的に動くので「絶対」を保証できない）。これは Phase 2 の機能強化として、コード側カフェインフィルタを追加する案を提示します。

- 現状（launch可能ライン）: 全ガードレールをプロンプトで制御
- Phase 2（推奨強化）: カフェイン除外のみコード側で事前フィルタし、二重防御にする

確信度: 高（プロンプト制御は実装済み。コード側フィルタは未実装の提案段階）

### Q2. ナレッジモデルの粒度の過不足

モデルの粒度は十分に構造化されており、大きな過不足はありません。今回 `ShopifyProduct` に story / category / origin / farm / cultivar / processing / tasteProfile（旨味・渋味・苦味・甘味・香ばしさ）/ caffeineLevel / brewingDifficulty / scenes / moods / brewingMethods / purposes / isSet を追加しました。

その上で、実データ投入時に検討いただきたい追加候補があります（今は無理に足さず、現実の商品データを見てから判断で構いません）。

- **容量・内容量**: 価格帯は持っていますが「何g/何包」が商品カードに無い。会話で「どれくらい入ってるの?」に答えにくい。
- **化粧箱対応フラグ**: 用途（purposes）に「ギフト」はありますが、ギフト適性をより正確に判断するなら「化粧箱対応か」のフラグがあると良い。
- **セット内容物リスト**: isSet=true の商品で「何が入っているか」を構造で持てると、初心者導線の説明がリッチになります（現状は description / story の自由文に依存）。

確信度: 高（現モデルで launch 可。追加は実データ次第の任意拡張）

### Q3. データ管理（Notion → Shopify → チャットボット）の妥当性

アーキテクチャとして妥当です。**Notion を単一の正（Single Source of Truth）とする**判断は正しく、一人運営での更新負荷を考えても理にかなっています。Shopify のメタフィールドを介して商品情報を共有する構想も、表記ゆれ防止・一貫性の観点で優れています。

チャットボット側の現在のDB（`InMemoryDataStore`）は、この構成における「チャットボット側キャッシュ」と位置づけられます。移行パスとしては以下を想定しています。

1. 当面: Notion から手動 CSV/JSON エクスポート → チャットボットの商品カタログへ取り込み
2. 将来: Notion API での自動同期

具体実装としては、**エクスポートした Notion データを受け取って商品カタログを更新する、シンプルな取り込み口（JSONファイル or インポート用エンドポイント）** を用意する案を提案します。いきなり双方向リアルタイム同期を作り込むのは過剰なので、まずは「手動エクスポート → 取り込み」で運用を回し始めるのが現実的です。

確信度: 高（思想は妥当。具体の取り込み口は未実装の提案段階）

### Q4. 競合時の優先順位で抜けている事故パターン

優先順位（①カフェイン > ②苦手/明示 > ③好み > ④初心者）はよく整理されています。その上で、ドキュメントに明示されていない事故パターンを2つ検出しました。

- **アレルギー・健康上の禁忌**: 例として「ミルク・料理」用途のお茶（ミルクティー想定）で、お客さんが乳アレルギーに言及した場合など。現状のガードレールはカフェインしか扱っておらず、アレルギーは抜けています。最優先（安全側）のガードレールとして「アレルギー・健康上の禁忌」を追加すべきと考え、未確定事項として §3 に挙げます。
- **相反するシグナルの同時提示**: 「初心者なんだけど、◯◯（特定品種）が欲しい」のように、④初心者と②明示指定が同時に出るケース。優先順位では「② > ④」で品種指定が勝ちますが、ボットは**両方のシグナルを言葉で受け止める**べきです（例:「初めてなら本当はセットが安心だけど、◯◯がいいなら単品で行こうか」）。優先順位ロジックだけだと、片方のニーズを無視した冷たい応答になりかねません。

確信度: 高（パターンの存在は確実。アレルギー対応は未実装の提案段階）

### Q5. 「押し売りしない」をLLMに守らせる方法

3つのアプローチがあり、今回は(1)を実装しました。

1. **システムプロンプトでの明示指示**（実装済み）: キャラクター設定に「商品の提案は基本1〜2点に絞る」「毎回売らなくてよい。会話が満ちることを優先する」を追加。さらに目安として「会話3往復に1回程度」のような頻度ガイドを足すことも可能です。
2. **NG例（ネガティブサンプル）の明示**（Phase 2）: 「こういう押し売りはダメ」という悪い例をプロンプトに入れると、LLMの逸脱が減ります。
3. **Few-shot（良い会話例の提示）**（Phase 2）: 理想的な雑談主・提案従の会話例を2〜3本入れてトーンを固定する。

重要な注意点: 現状この制約は**プロンプト上の「お願い」**であり、LLMが破る可能性はゼロにできません。確実に抑えたい場合は Phase 2 で「連続セールス言及回数をコード側でカウントし、一定回数を超えたら提案を抑制する」カウンター実装が必要です。launch 時点ではプロンプト制御で十分と判断しています。

確信度: 高（(1)は実装済み。(2)(3)とコードカウンターは未実装）

### Q6. この規模・一人運営体制で過剰/過小か

設計は規模に対して適切です。

- **Notion ベースのデータ管理**: 一人運営にとって賢い選択。専用管理UIを作り込むより、使い慣れた Notion で完結する方が運用が続きます。
- **過小な点**: 現在の実装（InMemory DB + ダミーseedデータ）は仕様に対して中身が足りていません。商品カタログに**実データが入っていない**のが最大のギャップです。属性は「もっともらしいダミー値」を入れてあるだけなので、藤井さんの実データで上書きが必要です。
- **ハードガードレール（プロンプト制御）**: launch には十分。
- **Shopify 同期**: 中程度の実装コスト。Phase 2 で問題ありません。

最大のリスクは **データ品質**です。商品属性（カフェイン量・味プロファイル等）が不正確だと、ガードレールがどれだけ精緻でも誤った提案になります（garbage-in, garbage-out）。仕組みより先に「正確な商品属性の整備」が効きます。

確信度: 高

## 4. 暗黙的要件・設計上の仮定

実装にあたり、こちらで置いた仮定です。誤りがあればご指摘ください。

- seed商品の属性値（味プロファイル・カフェイン等）は**こちらが文面から推測したダミー**で、実態を保証しません。実データでの上書き前提です。
- カフェイン除外の対象は「高・中」、許可は「低・ゼロ」と解釈しました（資料の「低/ゼロのみ提案可」に準拠）。
- 「明示属性指定」（産地・品種・農園・製法の名指し）は exact-match（完全一致）で絞る前提です。表記ゆれ（ひらがな/漢字等）は現状吸収しません。
- 「初心者にはセットを第一提案」は、淹れやすさ「シビア」の商品を主役にしないことと組み合わせて解釈しました。
- 営業ルールDB（旧 sales_rules）は廃止せず、「特別・キャンペーン用の補助」として残しました（商品カタログが主、こちらは従）。完全廃止すべきならご指示ください。
- ボットの一人称・口調（俺/〜だよね 等）は既存キャラクター設定を維持しています。藤井さん本人のアバターという位置づけと、この口調の整合は要確認です。

## 5. 文書で決まっていないと感じた箇所

資料（藤井さんのレコメンド設計）で明示されていなかった点です。

- **アレルギー・健康上の禁忌**の扱い（Q4で指摘）。
- **複数商品が全ガードレールを通過したときの最終決定基準**: 「シーン・気分で寄り添う1〜2点」とあるが、それでも2点に絞れない場合のタイブレーク（featured優先? セール優先? 価格? ランダム回避?）が未定義。現状は LLM 判断に委ねています。
- **「押し売り」の定量定義**: 何往復に1回までならOKか、の具体ラインが未定義。
- **在庫切れ・取り扱い停止時の挙動**: enabled=false で候補から外れますが、お客さんが名指しした商品が在庫切れの場合の応答文（謝罪 + 代替提案のトーン）が未定義。
- **多言語対応の有無**: 日本語前提で実装。インバウンド客対応の要否は未確認。
- **会話ログの活用方針**: ログは書き込むだけ（参照は将来フェーズ）。分析・改善にどう使うかが未定義。

### 6-B. モックモードで確認できなかったこと（Gemini 実APIが必要）

以下は `MOCK_CHAT=false`（Gemini 本番モード）でしか確認できないシナリオです。**実商品データをいただいた後、Gemini モードで改めて確認予定**です。

- 「朝にシャキッとしたい」→ *モックでは汎用返答になった*。Gemini 本番では商品の `scenes=["朝"]` / `moods=["シャキッと"]` を参照して静かなる覚醒の煎茶を選ぶはず（未検証）
- 「お茶初心者なんですが」→ *モックでは汎用返答になった*。Gemini 本番では `isSet=true` のスターターキットを第一候補に選ぶはず（未検証）
- 「役割と時間で語る」トーン（"夜、一日を静かに畳むときに" スタイル）が守られるか（LLM判断なので実APIでのみ評価可能）
- カフェイン・味プロファイルのハードガードレールがプロンプト制御で正しく機能するか
- 「毎回売らない」（雑談主・提案従）の体感

### 6-C. 藤井さんデータ受領後に行う予定のテスト

実商品データ（caffeineLevel・tasteProfile・正式ShopifyURL）をいただいたら、以下を Gemini 本番モードで確認する予定です。

2. 「カフェインゼロにして」で caffeineLevel="ゼロ" の商品だけが候補になること
