# AIチャットボット お茶レコメンド制御設計（外部レビュー用）

作成: 2026-06-18 ／ たゆまの茶荘・藤井
ステータス: **レビュー依頼ドラフト**（実装前の方針確認）

---

## 0. この文書の目的

たゆまの茶荘ECに導入するAIチャットボットについて、**「お茶のレコメンドをどう制御したいか」という方針**をまとめたものです。会話エンジンやUIの実装は貴殿（プロ）にお任せする前提で、**この制御の考え方が妥当か／実装上どう実現するのが良いか**をレビューしていただきたく作成しました。

末尾の「9. レビューしてほしいこと」に具体的な確認事項をまとめています。

---

## 1. プロダクトの哲学（前提）

- チャットボットは**代表（藤井）のアバターがオンライン上で接客する**という体験が核。単なるFAQ・検索ボットではない。
- お茶のトピックだけでなく、**音楽・漫画・ドラマ・グルメなど多様なカルチャーに精通した代表の知識**をAIに持たせ、会話を楽しみながら**自然にお茶を勧める**。
- ブランドの世界観は「アンチ・エナジードリンク」。スペック（効能・効率）でなく、**お茶が持つ時間と役割**を売る。よって推薦も「効きます」でなく「こういう時間に寄り添う」で語る。

---

## 2. 全体方針：ハイブリッド制御

レコメンドは2層で制御する。

- **ソフト層（会話で寄せる）**: 会話から汲んだシーン・気分・役割に合わせ、アバターが自然に1〜2点を勧める。
- **ハード層（絶対に外さないガードレール）**: 安全・満足・明確な要求に関わる条件は、会話の機微に関わらず機械的に強制する。

「会話の楽しさ（ソフト）」と「事故らない接客（ハード）」を両立させるのが狙い。

---

## 3. 商品ナレッジモデル

各商品を以下の属性を持つ1枚の「カード」として構造化する。**ガードレール判定用の属性**と**会話・語り用の属性**を兼ねる。

| 区分 | 属性 | 用途 |
|---|---|---|
| 識別 | 商品名／商品コード／カテゴリ（煎茶・玉露・ほうじ茶・和紅茶・番茶…） | 基本 |
| 語りの素材 | 産地／農園／品種／製法／一言ストーリー | 会話のフック・明示指定時はハード（§5-D） |
| 味プロファイル | 旨味・渋味・苦味・甘味・香ばしさ を各3段階（弱/中/強）でタグ化 | 味の好み制御（§5-B） |
| カフェイン度 | 高／中／低／ゼロ | カフェイン制御（§5-A） |
| 淹れやすさ | やさしい／ふつう／シビア | 習熟度制御（§5-C） |
| 合うシーン | 朝・仕事の合間・食後・夜・来客 など（複数可） | ソフト推薦 |
| 合う気分・役割 | シャキッと／落ち着き／甘い癒し／特別な時間 など | ソフト推薦 |
| 飲み方適性 | 急須／ティーバッグ／水出し／ミルク・料理 | ソフト推薦 |
| 用途 | 自分用／ギフト（化粧箱可否）／法人 | ソフト推薦 |
| 価格・容量 | 価格帯・内容量 | ソフト推薦 |
| セットフラグ | この商品が「詰め合わせセット」か | 習熟度制御（§5-C） |

設計上の意図:
- 味は単一の強弱でなく**5要素を独立タグ**にし、「渋いのは苦手だが旨味は欲しい」等の複合要望に応える。
- ラインナップは今後増える前提。**カードを1枚足すだけ**で拡張できる構造にしたい。

## 4. データ管理（マスターと配信）

二重管理を避けるため、**商品情報の編集を1箇所に集約**したい。

- **マスター = Notion「商品ストーリーDB」**（既存。商品名・コード・カテゴリ・価格・仕入先・本文を管理中）。ここに§3のチャットボット属性を**プロパティとして追加**する。
  - 採用理由: select / multi-select で**タグの選択肢を固定でき、表記ゆれが起きない**（ガードレール判定の安定に直結）。商品ストーリー本文の住所でもあるため、執筆と属性管理が1レコードに収まる。
- **配信先**:
  - Shopify: 既存フロー（Notion → Google Sheets → Shopify CSV）。味・カフェイン度・淹れやすさ・産地等は **Shopify metafield として商品ページにも表示**し、チャットボットと同じ値を共有。
  - チャットボット: 同じNotionレコードを書き出してナレッジカードにする。
- 当面はNotionの**手動CSVエクスポート**で運用し、品種が増えたら**Notion API同期**へ段階移行する想定。

> 既存の現物（Notion DBプロパティ・Sheets列構成・Shopify設定）は実装着手時に最新を確認する。本書は方針レベル。

## 5. ハードガードレール（決定的制御）

会話の前に機械的に効く層。「除外（絶対に勧めない）」と「必須（絶対に満たす）」で表現する。

### A. カフェイン
- トリガー: 「カフェイン抜きたい／夜だから／妊娠中／子どもにも」等
- ルール: カフェイン度 **「高・中」を候補から除外**。**「低・ゼロ」のみ**提案可。
- 補足: **控えめ（低カフェイン）まではOK**。完全ゼロ厳守ではない（ほうじ茶・和紅茶は可、煎茶・玉露・抹茶は外す）。

### B. 味の好み（苦手＝除外／好き＝必須）
- **苦手**: 明言された要素が**「強」の商品を除外**（例「渋いの苦手」→ 渋味=強 を外す）。
- **好き**: 明言された要素が**「強」の商品を必ず候補に含め、優先**（例「旨味が好き」→ 旨味=強 を当てにいく）。
- 苦手も好きも、どちらも厳守する。

### C. 習熟度（ビギナー → セット）
- トリガー: 「初心者／普段飲まない／よく分からない」等
- ルール: 淹れやすさ「シビア」の商品を**単品の主役にしない**。**詰め合わせセットを第一提案**にする（選ばせて迷わせない）。

### D. 明示的な属性指定
- トリガー: お客さんが**自分から**産地・品種・農園・製法を名指し（「鹿児島のお茶が」「やぶきたが飲みたい」「深蒸しがいい」等）。
- ルール: その属性に**合致する商品だけに絞る**（必須フィルタ）。合致なしなら、ごまかさず正直に伝えて近い代替を提案。

### 競合時の優先順位
1. **カフェイン除外**（安全）— 最優先
2. **苦手の除外 ＝ 明示的な属性指定**（お客さんの明確な要求）
3. **好きの必須**
4. **ビギナー → セット導線**

例:
- 「夜・カフェイン控えめで鹿児島の」→ カフェインが上位。鹿児島の中でも低カフェイン（ほうじ茶等）に絞る。なければ正直に伝える。
- 「初心者だけどやぶきたが飲みたい」→ 明示指定がビギナー導線に勝つ。やぶきたを出すが、淹れ方ガイドや水出しなど"失敗しない形"を添える。

## 6. ソフト推薦原則（アバターの勧め方）

§5で安全に絞った候補の中での振る舞い。

1. **主軸はシーンと気分**。味スペックの一致より、そのお茶が果たす**役割（時間・癒し・特別感）**で寄せる。
2. **スペックは"語りの素材"**。産地・農園・品種・製法は機能で押さず、物語のフックとして会話に溶かす（※お客さんが指定した場合は§5-Dのハードに切り替わる）。
3. **カルチャーから自然に橋を架ける**。雑談が主、推薦が従。
4. **押し売りにしない／毎回売らなくていい**。会話が満ちることを優先。
5. **提案は基本1〜2点に絞る**。選ばせず「あなたにはこれ」と差し出す。
6. **役割で語る言葉づかい**。「リラックスできます」でなく「夜、一日を静かに畳むときに」。

## 7. 想定する動作フロー（要件レベル）

エンジンの実装方法は貴殿に委ねるが、**満たしてほしい処理の意図**は以下。

1. 入口は雑談・カルチャー会話（用件から入らない）。
2. 会話から軸（シーン／気分／味の好み／カフェイン可否／習熟度／明示属性）を**継続的に読み取る**。質問攻めにしない。
   - 例外: **安全に関わるカフェインだけは曖昧なら自然に一言確認**。
3. お茶の要望が立ったら内部で:
   ```
   候補 = 全商品
    → §5 ハードガードレールで絞る
    → §6 ソフト原則でシーン・気分・役割に最も寄り添う 1〜2点を選ぶ
   ```
4. 提示は「役割と物語」で。Shopify商品ページへ自然にリンク。
5. 候補ゼロは正直に伝え、近い代替を提案。
6. 着地を急がない。

出力: 通常はアバターの会話テキスト。推薦時は会話＋商品（名前・一言の物語・商品ページリンク）、基本1〜2点まで。

## 9. レビューしてほしいこと

1. このハイブリッド制御（ハード＝機械的ガードレール＋ソフト＝LLMの会話判断）の切り分けは、実装上現実的か。ハード条件はプロンプトで縛るのか、コード側で候補を前フィルタするのが良いか。
2. §3のナレッジモデルの粒度は過不足ないか。チャットボットの推薦精度の観点で、足すべき／削るべき属性は。
3. §4のデータ管理（Notionマスター → Shopify metafield共有 → チャットボットKB）は妥当か。より良い単一ソースの持ち方はあるか。
4. §5の競合時の優先順位で、抜けている事故パターンはないか。
5. 「1回で売らなくていい・押し売りしない」という方針を、LLMにどう安定して守らせるか（指標・制御の知見があれば）。
6. 全体として、この規模・一人運営の体制で**過剰／過小**になっていないか。
